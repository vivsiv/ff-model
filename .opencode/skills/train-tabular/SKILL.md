# Train a tabular model

Train using the project's existing tabular pipeline and report the resulting MLflow run and evaluation. Respect user-supplied parameters and let the current code supply defaults for omitted values. Do not rebuild datasets, alter project code, evaluate the held-out test set, or start an MLflow UI unless separately requested.

## Resolve the request

1. Inspect the current `src/modeling/tabular/trainer.py`, `src/modeling/tabular/data_builder.py`, shared config schema in `src/modeling/data_builder.py`, and CLI help for supported parameters, defaults, and behavior. Run from the repository root. The current entry point is `uv run --no-sync python -m src.modeling.tabular.trainer`.
2. The CLI requires `--config`, a data-preparation YAML file; there is no code-default config or target. Use a user-specified config as-is. If the user supplies a target and data-prep options but no config, create a temporary YAML containing the target and only the requested options; omitted fields must remain omitted so `TabularModelDataBuilder` supplies its defaults. Explain that a target-only config uses code defaults, not the project's customized configs. If neither a config nor a target can be determined from the user's request, ask which to use; do not arbitrarily pick a file or target.
3. The data-prep config supports `target`, `positions`, chronological `split`, `sample_weights`, and `features`; consult its current schema before translating user inputs. If the user requests overrides to an existing config, create a separate temporary copy with only those explicit changes; preserve all other settings, do not edit the original, and report the effective changes. Validate config, target, requested positions, feature patterns, and values before starting. Do not claim a setting is supported if the current implementation ignores it.
4. Accept current CLI options: `--data-dir`, `--tracking-dir`, `--model-type`, `--param-grid`, and `--top-n-rows`. Pass only user-specified options so omitted values come from the CLI. Currently the defaults are `data`, `mlruns`, `random_forest`, no search, and top-N `[50, 100, 200]` respectively; these may change, so check the code. An explicitly empty top-N list must be passed as `--top-n-rows` with no numbers. Resolve paths relative to the repository root and preserve the user's tracking directory choice.
5. Current model types are `ridge`, `lasso`, `random_forest`, `svr`, `gradient_boosting`, and `linear`. Check the actual estimator's `get_params()` before accepting model hyperparameters. Model defaults are defined by `TabularModelTrainer.get_base_model()`, and can differ from raw scikit-learn defaults.

## Single fit versus search

- With no parameter grid or estimator overrides, use the CLI directly with the resolved `--config` and explicit user options. It fits one model and evaluates the **eval** split.
- `--param-grid` runs a **one-at-a-time** search, not a Cartesian grid: each value is fit separately with other estimator parameters at the project's base-model defaults. It registers a model version for each fit and logs parent/child MLflow runs. Validate the JSON grid and its keys and values; show the user the number of fits. Do not silently substitute a search for a request to fit one model with multiple hyperparameters together.
- The current search implementation hardcodes top-N `[50, 100, 200]` and does not pass the CLI's `--top-n-rows` through. If the user asks for a different top-N in a search, explain the limitation and ask how to proceed; do not pretend it was honored.
- If the user requests estimator parameters for **one fit**, the current CLI has no single-fit hyperparameter flag. Use the existing Python API rather than changing project code: construct `TabularModelDataBuilder` and `TabularModelTrainer`, call `setup_mlflow`, `fit_model(run_id, params=...)`, then `eval_model` on the eval split. Apply all requested parameters together. Preserve the CLI's current effective top-N default when omitted, because the Python method's own default may differ. Include the config-path metadata where applicable. If the user also supplies a grid, clarify the intended semantics rather than ignoring either input.

## Preflight, train, and report

1. Confirm the effective target's gold training CSV exists at `<data-dir>/gold/<target>__training_set.csv`, the requested config is readable, and the existing `uv` environment has the necessary packages. Check that the requested data and chronological train/eval splits are usable; explain any blockers. If data is missing, offer to use the `rebuild-data` skill, but do not initiate a rebuild without the user's request because it also refreshes upstream data.
2. Tell the user the effective model, target, config/overrides, input data, tracking directory, and search size if applicable. Training writes MLflow runs and registered model versions, evaluation predictions, and logs; a search does this for every fit. Use `uv run --no-sync` to avoid an unexpected dependency sync. If dependencies are missing, explain and ask before installing. Execute only a requested training run; do not modify unrelated files or remove previous experiments/models.
3. Capture command output, exit status, and the specific run IDs created by this invocation. Inspect those runs in the selected tracking store for metrics, registered model versions, and artifacts; do not assume the latest run belongs to this invocation if there are concurrent runs. If the run fails after creating artifacts, report the failure and partial outputs without deleting them or claiming success.
4. Summarize the actual configuration, model and hyperparameters, training/eval season ranges if verified, run ID(s), experiment and registered model/version, prediction artifact path, and eval RMSE/R² plus requested top-N metrics when present. Identify missing metrics rather than fabricating values, and distinguish eval metrics from test metrics. For a search report results per parameter/value and avoid implying the search selected a final champion unless it actually did. If requested, use `mlflow-ui` to locate or start the UI; do not assume it points at a non-default tracking store.

Example requests: `@train-tabular --config configs/ppr_points_per_game.yaml`, or `@train-tabular --config configs/fantasy_points_ppr.yaml --model-type ridge --param-grid '{"alpha": [100, 1000]}'`.
